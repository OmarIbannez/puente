# Plan: Puente v1, stablecoin payout ledger

**Date:** 2026-10-08
**Issue:** #1
**Discovery:** `docs/discovery/2026-10-08-puente-v1.md` (approved 2026-10-08)

## Summary

A Go and Postgres payout service. Stablecoin deposits (USDC; MXNB as a second asset) are credited
from a chain adapter, and payouts in pesos go out over a simulated SPEI rail through an idempotent
state machine and a transactional outbox. Every movement is posted to a multi-asset double-entry
ledger exactly once. A reconciliation job compares the chain, the rail and the ledger and reports
breaks. Ships with an API, a CLI, a React SPA, `docker compose up` with a seeded demo, and Render
plus Neon.

## Design

### Context

- The demo is public and anonymous, so it must work offline and must never spend real funds
  (discovery: *Constraints*, "Public demo safety").
- Reading real testnet deposits is cheap and safe. Sending needs operator funds (discovery:
  *Option A* result; *Rabbit Holes*, "Funding the live wallet").
- The public RPC caps `eth_getLogs` at 200 blocks (discovery: *Constraints*).
- MXNB has a verified testnet contract but no faucet (discovery: *Assumptions*, *Ruled Out*).
- Abono already has a proven ledger with a deferred balance trigger and idempotency middleware
  (discovery: *Relevant Files*, `abono/internal/ledger/post.go:62-121`,
  `abono/internal/api/idempotency.go:38-80`).
- The test ERC-20 and the in-process EVM both work (discovery: *Addendum*).

### Decision

**Option A from discovery.** Ports and adapters around four core packages, with the demo layers
(API, SPA, seed) on top.

**1. Money (`internal/money`).** `Asset` is `USDC`, `MXNB` or `MXN`. Each asset has a fixed scale:
6, 6 and 2. `Amount{Asset, Minor int64}` stores integer minor units only. FX rates are integers
scaled by 1e6 (MXN per 1 unit of the source asset). Conversion rounds toward zero to the centavo. The
remainder ("dust", reported by `money.Convert`) stays in the FX clearing position 3900, because
each asset balances on its own and a fraction of a centavo can't be posted. No floats anywhere. MXNB→MXN is 1:1 at its scale (6dp→2dp),
which leaves sub-centavo dust.

**2. Ledger (`internal/ledger`).** Ported from abono and made multi-asset:
- Every posting carries `asset`. Each entry must sum to zero **per asset**. That rule is checked
  in Go and again by a deferred constraint trigger at commit.
- `journal_entries.ref` is unique per sandbox (for example `payout:<id>:submit`,
  `deposit:<transfer_id>`). `Post` uses `ON CONFLICT (sandbox_id, ref) DO NOTHING` and returns
  `(id, posted bool)`. This is the **exactly-once posting** guarantee: retries can call `Post`
  freely.

Chart of accounts (each account holds one or more assets):

| Code | Account | Type | Assets |
|---|---|---|---|
| 1010 | Hot wallet (on-chain) | asset | USDC, MXNB |
| 1100 | SPEI settlement account | asset | MXN |
| 2010 | Customer balances | liability | USDC, MXNB |
| 2020 | Payouts reserved | liability | USDC, MXNB |
| 2100 | SPEI payouts in flight | liability | MXN |
| 3000 | Treasury equity (MXN prefunding) | equity | MXN |
| 3900 | FX conversion clearing | equity | all |
| 4100 | Payout fee income | revenue | USDC, MXNB |

Entry catalog:

| Ref | Postings |
|---|---|
| `funding` | Dr 1100 / Cr 3000 (MXN): treasury prefunds the SPEI account |
| `deposit:<transfer>` | Dr 1010 / Cr 2010 (asset) on confirmation |
| `deposit_reversal:<transfer>` | the inverse, when a credited transfer is orphaned by a reorg |
| `payout:<id>:reserve` | Dr 2010 / Cr 2020 (source asset: amount + fee) |
| `payout:<id>:submit` | Dr 2020 / Cr 4100 (fee) + Cr 3900 (amount); Dr 3900 / Cr 2100 (MXN) |
| `payout:<id>:settle` | Dr 2100 / Cr 1100 (MXN) on *liquidado* |
| `payout:<id>:release` | reverses reserve (and submit, when the rail rejected it) |
| `payout:<id>:return` | *devuelto* after *liquidado*: Dr 1100 / Cr 3900 (MXN); Dr 3900 / Cr 2010 (source asset at the original rate; the fee is kept) |

Invariants: per-asset trial balance is zero; 2020 per payout equals its reserved amount while it is
in flight; account 1100 equals the rail's statement balance.

**3. SPEI (`internal/spei`).**
- `clabe.go`: validation ported from `xolo/validators.py:97-162`, plus a small bank catalog.
- `rastreo.go`: clave de rastreo generator (≤30 chars, `PNTE` + date + sequence).
- `sim.go`: a simulated participant with its own tables (`spei_orders`, `spei_statement`), standing
  in for the bank's books. That makes it an independent source for reconciliation.
- `Submit(clave, ...)` is idempotent on the clave.
- Outcomes are deterministic from SHA-256(sandbox, clave) plus per-sandbox fault flags:
  `timeout` (accepted, but the ack is lost), `rechazado` (with a reason such as "cuenta
  inexistente"), `liquidado` (with a CEP-like receipt), and `devuelto` some ticks after
  liquidado.
- Status set: `en_proceso`, `liquidado`, `rechazado`, `devuelto`. Everything is labeled simulated
  (discovery: *Rabbit Holes*, "SPEI realism").

**4. Chain (`internal/chain`).** The `Source` interface returns `Transfer{chain_id, token,
tx_hash, log_index, block_number, block_hash, from, to, amount}` plus a `Head`. There are two
adapters:
- `chain/sim`: per-sandbox simulated blocks in Postgres. "Send test deposit" in the UI and the
  seed create transfers. Fault flags can inject a duplicate log, a short amount, or a reorg that
  replaces a block.
- `chain/evm`: go-ethereum `ethclient`. Scans the token's `Transfer` logs to watched addresses in
  pages of ≤200 blocks from a stored cursor, and treats a log as confirmed after N blocks. A
  rescan compares the stored `block_hash` to detect reorgs. Configured per asset (USDC: Base
  Sepolia 84532; MXNB: Arbitrum Sepolia 421614).

`chain_transfers` is unique on `(chain_id, tx_hash, log_index)`, so ingestion is idempotent.
Sending (`evm.Send`) is **CLI-only** and needs `PUENTE_HOT_WALLET_KEY`; the API never sends. Live
reads feed a fixed, read-only "live" sandbox that every visitor can view.

**5. Payouts (`internal/payout`).**

```
create ─► reserved ─► submitted ─► liquidated (terminal success)
             │            │  └──► returned (devuelto; compensating entry)
             │            ├──► rejected ─► released
             │            └──► needs_review (retries exhausted, outcome unknown)
             └──► released (cancel before submit)
```

- `POST /payouts` (with an Idempotency-Key) creates the payout, quotes the FX rate, posts
  `reserve`, and inserts an **outbox** row, all in one transaction. Insufficient balance → 422.
- A worker claims outbox rows with `FOR UPDATE SKIP LOCKED`. It posts `submit` and calls
  `spei.Submit` with the payout's fixed clave.
- A timeout is retried with exponential backoff and the **same clave**. The rail dedupes, and the
  ledger dedupes by ref. After 5 attempts the payout goes to `needs_review`.
- Rail status changes are polled per tick and applied through the same transition function. Each
  transition locks the payout row, checks that the edge is legal, writes an event, and posts its
  entry in one transaction.

**6. Deposits (`internal/deposit`).** Confirmed transfers to a known customer address are posted
as `deposit:<id>`. Orphaned transfers that were already credited get a reversal, and the customer
can go negative. That surfaces as a recon break rather than being hidden.

**7. Reconciliation (`internal/recon`).**
- A run (scheduled by the worker every 5 minutes per active sandbox; also triggered by
  `POST /recon/runs` and `puente recon run`) matches three sources:
  - chain transfers ↔ deposit entries
  - rail orders ↔ payout entries and states
  - ledger account 1100 balance ↔ rail statement balance
- Break kinds: `missing_on_ledger`, `missing_on_chain`, `missing_on_rail`, `duplicate`,
  `amount_mismatch`, `balance_mismatch`.
- Results go to `recon_runs` and `recon_breaks`.
- Runs are read-only: no auto-fixing in v1. Breaks show the evidence (tx hash and explorer link,
  clave, entry ids).

**8. Runtime.**
- `puente serve` runs the HTTP API plus an in-process worker loop (outbox, rail poll, chain scan,
  recon). The worker for each sandbox is also callable synchronously as `Tick(ctx, sandbox)`,
  which tests and the demo's "Advance" button use.
- Sandboxes, idempotency, error shape, static SPA and health are ported from abono.
- Config: `DATABASE_URL`, `PORT`, `PUENTE_SEED_DEMO`, `PUENTE_LIVE_USDC_RPC`,
  `PUENTE_LIVE_MXNB_RPC`, `PUENTE_LIVE_WATCH_ADDRESS`, `PUENTE_HOT_WALLET_KEY` (CLI send only),
  `PUENTE_CONFIRMATIONS`.

### Consequences

- The demo always works offline and can show every break kind on demand. Real on-chain evidence
  comes from the live, read-only sandbox.
- The ledger, outbox and recon core doesn't depend on the demo layer, so the planned "US–MX
  cross-border payout orchestrator" project can reuse it.
- Ports and adapters give the architecture doc a strong "alternatives considered" section
  (Option B live-only, Option C hand-rolled signing, Stellar/XRPL).
- Tests are deterministic: the simulated rail and chain are seeded by hashes, the EVM adapter
  tests use the in-process `ethclient/simulated`, and DB tests use testcontainers Postgres.

### Drawbacks

- There are two chain implementations and a rail simulator to maintain. That's more code than a
  single real integration.
- go-ethereum adds about 177 modules to the build (266 with test-only `simulated`) and a 13 MB
  binary.
- The live mode only shows deposits to one operator address. Visitors can't run a live payout end
  to end.
- The SPEI simulator isn't conformant with Banxico's spec. It's labeled as such.
- An in-process worker plus Render's free tier sleeping means scheduled recon only runs while the
  service is awake. Acceptable for a demo; the doc states it.

## Topology

**Recommendation:** FORK in waves of at most 2 concurrent subagents, launched 30 s apart:

- Wave 1: Task 1 (DIRECT, by me). It sets the conventions every other task copies.
- Wave 2: Tasks 2 and 3. Then Task 4 when a slot frees up.
- Wave 3: Tasks 5 and 6.
- Wave 4: Task 7, then Task 8 (DIRECT: these integrate everything).
- Wave 5: Tasks 9 and 10 in parallel.
- Wave 6: Task 11, then Task 12.

**Rationale:** Tasks 2, 3 and 4, and later 5 and 6 and later 9 and 10, touch disjoint packages and
only share migrations. Migrations are pre-numbered per task, so there are no file conflicts. Tasks
7 and 8 cut across every package and are better done with full context. TEAM isn't needed because
nothing shares mutable state during development.

There are 12 tasks, more than the 10-task heuristic. They're kept as one plan because the
showcase only has value end to end (API, SPA, deploy). If you'd rather phase it, the natural cut
is v1a = Tasks 1–9 (headless core, CLI, API) and v1b = Tasks 10–12.

## Acceptance Criteria

Copied from discovery:

- [ ] Unbalanced entry rejected in Go and by the deferred trigger: `go test ./internal/ledger -run Unbalanced`
- [ ] Idempotency replay, 422 and 409 semantics: `go test ./internal/api -run Idempotency`
- [ ] Ten concurrent creates with one key → one payout: `go test -race ./internal/api -run ConcurrentPayout`
- [ ] Legal FSM transitions only, entry in the same transaction: `go test ./internal/payout -run Transitions`
- [ ] Rail retry exactly once on the ledger: `go test ./internal/payout -run RetryExactlyOnce`
- [ ] Devolución → compensating entry: `go test ./internal/payout -run Devolucion`
- [ ] Idempotent chain ingestion, reorg detection: `go test ./internal/chain/... -run Rescan`
- [ ] Recon finds each seeded break and nothing on a clean world: `go test ./internal/recon`
- [ ] Trial balance zero everywhere: `go test ./... -run TrialBalance`
- [ ] CLI subcommands: `go test ./cmd/puente`
- [ ] `docker compose up` serves the seeded SPA in under 60 s: `just smoke`
- [ ] Full gate: `inertclaude ci`
- [ ] Design-review architecture doc and README: manual review
