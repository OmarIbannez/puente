# Discovery: Puente v1, stablecoin payout ledger

**Tracked in:** #1 · Notion card: [3. Stablecoin payout ledger in Go (+ MXNB/SPEI reconciliation)](https://app.notion.com/p/3f2e5630e5e3817d8996efcbcaf6b01c)

## Problem Statement

Build a showcase payout service in Go, backed by Postgres. A client asks to pay a Mexican beneficiary
in pesos, funded by stablecoin. Puente:

1. receives stablecoin (USDC, optionally MXNB) at a deposit address on a testnet,
2. records every movement in a double-entry ledger,
3. runs an idempotent payout state machine that pays out over a simulated SPEI rail, and
4. reconciles on-chain transfers and SPEI settlements against the ledger, flagging breaks:
   missing, duplicate and amount mismatch.

Deliverables: an HTTP API, a CLI, a React SPA, an architecture doc written as a design review,
`docker compose up` with seeded data, and a public demo on Render with a Neon database.

It closes the "no payments infrastructure" gap for Jeeves, Bitso and Félix at Principal Backend
level (from the Notion card's *Job hunt benefit*).

## Appetite

**Large (about 1 to 2 focused weeks of agent work).** The Notion card says "L (3+ weeks)". Abono,
built the same way, reached v1 locally within a day (see the abono memory note), so most of the
structure is known. The budget covers the ledger, the payout FSM, chain ingestion, the SPEI
simulator, reconciliation, the SPA, deployment and docs. It does not cover real money movement
or a production Juno integration.

## Constraints

- **Quality gate is `inertclaude ci`, which runs `just ci`.** Polyglot repos put every check in

  (free-hosting memory note).
- **Hosting: Render's one free Postgres slot is taken by Abono** (`abono/render.yaml`, abono memory

- **Showcase rules (user-profile memory note):** a codename repo, a React SPA, Render, clone and
  `docker compose up` with seeded data, personal GitHub `OmarIbannez` through a per-repo deploy
  key with `ssh -F /dev/null`. Never touch global git or SSH config. No AI attribution in

- **Public demo safety:** anonymous visitors must not be able to spend real testnet funds or

## Acceptance Criteria

- [ ] A journal entry that doesn't sum to zero is rejected both in Go and at commit time by a
      deferred Postgres constraint trigger. Test: `go test ./internal/ledger -run Unbalanced`
- [ ] The same `Idempotency-Key` with the same body replays the stored response byte for byte with
      `Idempotent-Replay: true`. A different body returns 422; a request still in flight returns
      409. Test: `go test ./internal/api -run Idempotency`
- [ ] Ten concurrent create-payout calls with one key produce exactly one payout and one set of
      ledger entries. Test: `go test -race ./internal/api -run ConcurrentPayout`
- [ ] The payout FSM only allows legal transitions (see Approach A), and every transition posts its
      ledger entry in the same transaction as the state change. Test:
      `go test ./internal/payout -run Transitions`
- [ ] Rail retries are exactly-once on the ledger: a SPEI timeout followed by a retry with the same
      `clave de rastreo` never double-posts. Test: `go test ./internal/payout -run RetryExactlyOnce`
- [ ] SPEI devolución (return) after liquidación reverses the payout through a compensating ledger
      entry, never by deleting rows. Test: `go test ./internal/payout -run Devolucion`
- [ ] Chain ingestion is idempotent per `(chain_id, tx_hash, log_index)`. Re-scanning a range adds
      nothing, and a reorg deeper than the confirmation depth is detected. Test:
      `go test ./internal/chain -run Rescan`
- [ ] Reconciliation reports `missing_on_ledger`, `missing_on_rail`, `duplicate` and
      `amount_mismatch` breaks for seeded faults, and a clean run reports zero. Test:
      `go test ./internal/recon`
- [ ] The trial balance is zero after the seeded demo and after every test scenario. Test:
      `go test ./... -run TrialBalance`
- [ ] The CLI covers `migrate`, `serve`, `seed`, `payout create`, `recon run` and `ledger balance`.
      Test: `go test ./cmd/puente`
- [ ] `docker compose up` serves the seeded SPA on :8000 within 60 s. Test: `just smoke`
      (curl `/api/health` and `/api/payouts`)
- [ ] The full gate passes: `inertclaude ci`
- [ ] `docs/architecture.md` follows design-review structure (context, goals and non-goals,
      design, alternatives considered, failure modes, open questions), plus a README with a
      quickstart and screenshots. Test: manual review.

## Non-Goals

- **Real money or mainnet.** Testnets and a simulated rail only.
- **A real SPEI or STP or Juno integration.** Juno requires KYB before minting or redeeming
  ([Privy MXNB guide](https://docs.privy.io/recipes/bitso-mxnb-onramp)). Its staging environment
  needs a signed-up account. Both are out of scope for a public demo.
- **FX pricing engine.** One static or configurable USD/MXN rate. Xolo already does Banxico FIX.
- **KYC/AML screening.** Sentinel covers that; Puente could call it later.
- **Custody or key-management product.** One hot wallet key from env, for the optional live
  mode only.
- **Multi-chain in v1.** One live chain (see candidates). MXNB is a second asset on a second
  chain, scoped as an extension.

## Rabbit Holes

- **Funding the live wallet.** Circle's faucet hands out testnet USDC
  ([Circle USDC addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses)).
  Gas needs Base Sepolia ETH from a separate faucet, and those often require a mainnet balance
  or captcha. *Mitigation:* live sending is opt-in, funded once by hand. The public demo
  defaults to the simulated chain.
- **MXNB testnet tokens.** MXNB is live on Arbitrum Sepolia (verified below), but I found no
  faucet. Getting tokens means a Juno sandbox account
  ([Juno docs](https://docs.bitso.com/juno/docs/create-clabes) mention mock SPEI deposits, but they
  need account setup). *Mitigation:* support MXNB as an asset on the simulated chain, plus
  read-only watching of the real Arbitrum Sepolia contract. No live MXNB sending unless the user
  gets Juno sandbox access.
- **Public RPC `getLogs` 200-block cap.** *Mitigation:* the scanner pages in ≤200-block windows
  with a stored cursor and confirmation depth.
- **Reorgs and finality.** On L2 testnets, reorgs are rare but possible. *Mitigation:* credit
  deposits only after N confirmations, and keep `block_hash` so a rescan can detect a changed
  block.
- **SPEI realism.** I couldn't find Banxico's official devolución reason catalog or the CEP
  technical format in this pass (search results were secondary sources). *Mitigation:* model the
  status set from public sources (en proceso → liquidado | rechazado | devuelto), plus clave de
  rastreo (≤30 chars), a CLABE check digit and a CEP-like receipt. Label it "simulated" and don't
  claim conformance with the Banxico spec.
- **go-ethereum weight.** It adds about 177 modules and a 13 MB binary (spike below), and adds
  supply-chain and lint surface. *Mitigation:* confine it to `internal/chain/evm`. Option C below
  avoids it.
- **Money precision.** USDC and MXNB use 6 decimals on-chain; SPEI moves centavos (2 decimals).
  Converting between them must use exact integers and an explicit rounding rule, with
  conversion dust booked to an account. That gives reconciliation a real `amount_mismatch` case
  instead of float noise.

## Approach Candidates

All candidates share the same core: a Postgres double-entry ledger (abono's pattern, but
multi-currency, with one row per posting carrying `asset` in minor units), abono's idempotency
middleware, and a payout FSM:

```
created → funds_reserved → submitted_to_rail → liquidated → completed
                         ↘ rejected → released            ↘ devuelto → reversed
          (rail timeout → retry with same clave de rastreo, bounded, then → needs_review)
```

They differ in **how the chain side is sourced**, the main unknown.

### Option A: Pluggable chain adapter, simulated by default, live Base Sepolia read and opt-in send (recommended)

- **How:** `chain.Source` interface with two implementations:
  1. `simchain`: a deterministic in-DB chain per sandbox. It has blocks, tx hashes, confirmations
     and fault injection (duplicate log, short amount, reorg). The public demo and compose run
     on it, offline.
  2. `evm`: go-ethereum `ethclient`. It scans USDC `Transfer` logs to the deposit address in
     ≤200-block pages after N confirmations. Optional: send USDC from an env-configured hot
     wallet (operator-only, never anonymous).

  Tests use `ethclient/simulated` for the `evm` adapter, including reorg tests via `Fork`.
- **Hypothesis:** go-ethereum can read real testnet USDC transfers with a small amount of code,
  and has an in-process EVM for tests.
- **Experiment:** a spike in the scratchpad (`ethspike/main.go`) dialed `https://sepolia.base.org`,
  ran `FilterLogs` for `Transfer(address,address,uint256)` over 150 blocks, fetched a receipt and
  generated a key. Separately, I checked `ethclient/simulated` exists in v1.17.8.
- **Result:** `head 47877417 transfer logs in 150 blocks: 267`. Then
  `tx 0xde7c…649e logIndex 10 … amount 1000` and `receipt status 1 block 47877267`. The build took
  15 s cold, the binary is 13 MB, and `go list -m all` shows 177 modules. `simulated.NewBackend`,
  `Commit`, `Fork` and `Rollback` exist (`backend.go:75-199`).
- **Learning:** Reading real deposits is easy and needs no funded wallet. A visitor (or you) can
  send testnet USDC to the demo's deposit address and watch it reconcile. Sending is the only
  part that needs funds, so it stays opt-in.
- **Trade-offs:** + The demo always works (simulated), and real on-chain evidence is available
  (live read). + Fault injection makes reconciliation breaks demonstrable on demand. + Strong
  design-review story (ports and adapters, finality, reorgs). − Two chain implementations to
  maintain. − go-ethereum dependency weight.
- **Risk:** `simchain` could feel "fake" to reviewers. Mitigate with the live-read mode and the
  README showing a real Base Sepolia tx reconciled.

### Option B: Live-only Base Sepolia (no simulated chain)

- **How:** Only the `evm` adapter. Seed data comes from real past testnet transactions; the demo
  shows them read-only.
- **Hypothesis:** Real testnet activity is enough to populate a demo.
- **Experiment:** same spike plus the `eth_getLogs` range probe.
- **Result:** There's plenty of USDC activity (267 transfers in 150 blocks). But the public RPC
  caps `getLogs` at 200 blocks (`-32614`), and those transfers are other people's, unrelated to
  Puente payouts.
- **Learning:** You can't inject faults on a real chain, so the reconciliation breaks (the
  showcase point) can't be demonstrated on demand. Compose would also need internet and an RPC
  key to avoid rate limits.
- **Trade-offs:** + Maximally "real". − No offline `docker compose up`. − Breaks can't be seeded.
  − Per-visitor sandboxes become meaningless on a shared chain.
- **Risk:** High demo fragility (RPC limits, faucet dependence).

### Option C: Option A without go-ethereum (hand-rolled JSON-RPC and signing)

- **How:** Raw JSON-RPC over `net/http` for `eth_getLogs`, `eth_call` and `eth_blockNumber`
  (proven by the curl probes above). Signing EIP-1559 txs with
  `github.com/decred/dcrd/dcrec/secp256k1/v4` (v4.4.1) plus `golang.org/x/crypto/sha3` (v0.57.0)
  and a small RLP encoder.
- **Hypothesis:** Reads need no library. Signing needs about 300 lines plus test vectors.
- **Experiment:** the curl RPC probes worked (results above). Module versions confirmed via
  proxy.golang.org. The signing path wasn't spiked.
- **Result:** Reads are trivially feasible. Signing is unproven.
- **Learning:** Reads are a good fit for hand-rolling. Signing is a correctness risk (RLP,
  `v` recovery id, chain id) with no showcase value over using go-ethereum, and no in-process
  EVM for tests.
- **Trade-offs:** + Tiny dependency graph. − Loses `ethclient/simulated`. − Crypto code to own.
- **Risk:** Subtle signing bugs; rabbit hole.

### Ruled Out

- **Stellar or XRPL testnet as the primary chain.** USDC on Stellar mirrors Félix (Notion card),
  and the card mentions MXNB on XRPL. But MXNB's documented testnet is **Arbitrum Sepolia**
  (Bitso docs, verified on-chain above), and Base Sepolia USDC is verified and EVM-compatible.
  Keeping one EVM adapter lets one code path serve USDC (Base Sepolia) and MXNB (Arbitrum
  Sepolia) by config (chain id, RPC URL, token address). Stellar stays a future adapter in the
  design doc's "alternatives considered".
- **Live MXNB sending in v1.** No faucet found, and Juno needs KYB/sandbox sign-up (Privy guide,
  Juno docs). Read-only watching of the real contract is still possible.

## Recommendation for DESIGN & PLAN

Option A, with MXNB in v1 as a **second asset**: simulated for payouts, plus read-only watching
of the real Arbitrum Sepolia contract. Abono's ledger and idempotency patterns are ported, not
imported (separate repo, multi-currency ledger). Per-visitor sandboxes as in Abono. A scheduled
reconciliation job plus an on-demand run from the SPA and the CLI.
